# Caret 后续维护与改进计划

> 文档性质：维护交接与后续改进依据  
> 适用范围：当前 Electron + React + FastAPI 重构版，以及独立授权端  
> 更新日期：2026-07-18  
> 状态：2026-07-18 已完成首轮实施与自动化验收；后续按月维护

## 1. 目标与维护原则

本轮维护的目标不是重写已经正常工作的业务能力，而是消除未来升级阻塞、降低交付风险，并使测试、文档和依赖维护形成可持续流程。

实施时遵循以下原则：

1. **以复用为荣，以重写为耻。** 已有成熟、持续维护且许可证合适的模块，应优先复用；项目代码主要负责 Caret 特有的业务编排与必要胶水逻辑。
2. **不因依赖较多而主动重写成熟能力。** 只有出现明确的安全漏洞、停止维护、无法打包、严重性能瓶颈或功能不满足需求时，才评估替换依赖。
3. **小步、独立、可回滚。** 时间处理、依赖迁移、安装链路、前端性能、文档治理应拆成不同批次，不在一个提交中混杂处理。
4. **行为不退化。** 所有依赖升级和兼容迁移必须先锁定当前行为，再验证迁移前后结果。
5. **现役代码与历史代码保持隔离。** 后续开发只落在 `app/`；`legacy/` 是只读历史参考，不得成为现役代码的运行时依赖。
6. **品牌对外统一。** 所有用户可见内容统一使用英文品牌名 `Caret`，不再使用中文品牌名“句读”。

## 2. 已确认的技术边界

### 2.1 保留 LangChain 生态组件

当前没有移除 LangChain 的计划，也不应自行重写它已经提供的成熟能力。

现有职责包括：

- `langchain_text_splitters.RecursiveCharacterTextSplitter`：对知识库资料进行递归切块；
- `langchain_community.retrievers.BM25Retriever`：提供 BM25 关键词检索；截至 2026-07-18 上游尚无官方独立继任包，`langchain-classic` 仅为弃用转发层，暂不迁移；
- `langchain_core.documents.Document`：承载知识块文本与来源元数据。

后续如果出现弃用警告，应先定位到具体类、方法或导入路径，再根据官方迁移说明处理：

- 官方将功能拆分到新包：迁移到官方继任包；
- 只是调用方式变化：更新调用方式并做行为回归；
- 警告来自依赖内部且暂无迁移路径：记录并等待上游修复；
- 不得把“出现弃用警告”等同于“整个 LangChain 或 `langchain-community` 即将退役”。

除非有独立证据支持，否则不自行实现 `RecursiveCharacterTextSplitter`、`BM25Retriever` 或等价替代品。

### 2.2 区分 SaT 分句与知识库切块

项目中存在两个目的不同的文本处理过程，维护时不得混为一谈。

#### 医学文稿分句

- 对象：用户上传、等待 AI 审校的医学文稿；
- 目的：识别自然语句边界；
- 实现：MIT 许可的 SaT `sat-3l-sm`，通过 `wtpsplit.SaT` 调用；
- 降级：模型无法加载或推理失败时，回退到中文标点正则；
- 后处理：短句合并、章节识别、参考文献识别和审校块组装。

实现位置：`app/server/app/pipeline/segment.py`。

#### 医学知识库切块

- 对象：上传到知识库的 PDF、TXT、CSV、DOCX 等资料；
- 目的：生成适合向量化和 RAG 检索、具有适当上下文的知识块；
- 实现：LangChain `RecursiveCharacterTextSplitter`；
- 当前参数：`chunk_size=500`、`chunk_overlap=50`；
- 后续链路：BGE-M3 向量化 → LanceDB 向量索引 → BM25 索引 → RRF 融合检索。

实现位置：`app/server/app/rag/index.py` 与 `app/server/app/rag/store.py`。

SaT 自然句分割与 RAG 固定长度重叠切块解决的是不同问题，不能相互替代。

### 2.3 Bundle 只记录趋势，不设硬预算

当前 renderer 主 bundle 约 951 KB。该数字需要结合压缩尺寸、解析耗时和 Electron 本地加载特点判断，不能单独作为质量结论。

后续可以记录：

- 主 bundle 原始尺寸；
- gzip 后尺寸；
- 各页面异步 chunk 尺寸；
- 从启动到主窗口可交互的时间；
- 首次进入审校工作台的时间；
- 相邻版本的体积与启动耗时变化。

不设置固定体积上限，不因超过某个数字让 CI 失败。只有出现无法由正常功能增长解释的明显跃升时，再人工分析。

页面懒加载属于可选优化，应以实际启动体验为依据，不为了追求更小数字而过度拆分。

### 2.4 品牌统一为 Caret

所有用户可见内容统一使用 `Caret`：

- 应用窗口标题、启动画面和托盘提示；
- 安装包、桌面快捷方式和开始菜单；
- 使用指南、授权管理指南和交接文档；
- 授权端可使用 `Caret License Center`；
- 后端展示名称可使用 `Caret Backend`；
- 中文说明可以描述“医学文稿 AI 审校桌面应用”，但不再创造或使用中文品牌名。

以下内部兼容标识不应只为品牌统一而立即修改：

- GitHub 仓库名和本地目录 `AI-Review-win`；
- Electron `appId`；
- 已在使用的环境变量前缀；
- 用户数据目录、数据库位置及升级识别标识；
- 已发布客户端与授权端之间使用的协议字段。

这些标识如需调整，应单独设计迁移方案，避免破坏已有安装、配置、数据和授权关系。

## 3. 后续维护事项

### P0：建立可重复的质量基线

先记录当前状态，再进行兼容迁移。建议将检查拆分为独立任务：

1. TypeScript 类型检查；
2. Electron 许可证测试；
3. 业务后端 pytest；
4. 授权端 pytest；
5. Electron/Vite 构建；
6. Node 与 Python 依赖安全审计；
7. 安装、启动、托盘退出和卸载冒烟检查；
8. 文档一致性与 `legacy/` 边界检查。

每次基线记录至少包括：通过、失败、跳过、警告数量，构建产物大小，以及各命令的退出码。

### P1：治理 Python 弃用警告

此前后端测试虽通过，但观察到约 240 条弃用警告。正式实施前应重新运行测试并分类统计，不能仅凭总数处理。

#### `datetime.utcnow()`

目标是统一时间语义，而不是机械替换调用：

- 业务逻辑内部统一使用带时区的 UTC；
- 数据库存储统一为 UTC；
- API 使用包含时区的 ISO 8601；
- 前端展示时再转换为本地时间；
- 重点验证许可证到期、心跳、离线宽限和时间回拨逻辑；
- 如果旧数据库保存的是 naive datetime，需要提供兼容读取或迁移策略。

建议集中封装时间来源，避免业务代码散落调用 `datetime.now()` 或 `datetime.utcnow()`。

#### Starlette TestClient / httpx

根据实际警告迁移测试客户端，并确保迁移后仍真实执行 FastAPI lifespan：

- 数据库初始化；
- 僵尸任务状态收敛；
- 授权密钥初始化；
- 限流器初始化；
- shutdown 清理。

业务后端与授权端应各自提供统一测试 fixture，避免每个测试文件重复构造客户端。

#### LangChain 相关警告

只处理具体弃用点，遵循官方迁移路径。迁移前后验证：

- 相同知识库文件产生的 chunk 数量与边界；
- 中文分隔符和 overlap 行为；
- BM25 top-k 结果；
- 向量 + BM25 + RRF 的融合顺序；
- BM25 持久化文件的兼容性；
- PyInstaller 打包后的索引与检索功能。

警告治理采用“存量记录、新增可见、逐步下降”的方式。不得全局忽略所有 `DeprecationWarning`。

### P1：迁移 Electron 镜像配置

当前 `.npmrc` 中的 `ELECTRON_MIRROR` 已被 npm 提示未来不再支持。建议：

- 从 `.npmrc` 移除非 npm 标准配置项；
- 通过真正的进程环境变量向 Electron 下载器传递 `ELECTRON_MIRROR`；
- 提供 Windows 安装依赖脚本，临时设置镜像、执行安装并恢复原环境；
- CI 使用任务级环境变量；
- 官方源可用时允许完全不设置镜像；
- 文档明确镜像只影响依赖下载，不属于运行时配置。

验收要求：

- npm 不再产生未知配置警告；
- 清理 Electron 下载缓存后仍能安装；
- 官方源与镜像源两种路径均可工作；
- `npm ci` 可重复执行。

### P2：前端加载优化与趋势记录

先记录真实启动数据，再决定是否引入路由级 `React.lazy` / `Suspense`。

优先候选为四个独立页面：文档库、审校工作台、医学知识库、设置。优化后需检查：

- Electron `file://` + HashRouter 路由正常；
- 页面首次加载没有空白或明显闪烁；
- 页面间跳转和状态恢复正常；
- 开发模式与打包模式行为一致；
- 没有为了拆包产生大量微小 chunk。

本项不设置硬性 bundle 预算，也不作为当前阻塞项。

### P2：品牌与文档一致性

在现役代码和文档中搜索以下历史名称：

- `句读 Caret`；
- `句读`；
- `AI 审校助手`；
- 其他旧产品标题。

处理时分类：

1. 当前 UI、打包配置、使用文档和交接文档：统一为 `Caret`；
2. 历史设计决策或迁移记录：允许保留，但应明确其历史属性；
3. `legacy/` 原始档案：保持只读，不因品牌更新批量改写。

架构文档还应覆盖后来新增的授权系统，清楚描述：

- Caret 客户端；
- 本地 FastAPI sidecar；
- 独立授权端；
- 客户端许可证校验；
- 激活、心跳、刷新、离线宽限与吊销链路。

### P2：强化 `app/` 与 `legacy/` 边界

建议增加机器可检查的规则：

- `app/` 不得 import、require 或动态加载 `legacy/`；
- 测试不得依赖旧版虚拟环境和旧版运行数据；
- 打包产物不得包含 `legacy/` 与 `archive/`；
- 修改 `legacy/` 时需要明确说明原因并额外审核。

如需移植旧版业务逻辑，应在 `app/` 中重新实现并补测试，但不得建立运行时耦合。

### P3：形成周期性维护节奏

建议每月执行：

- Node 与 Python 依赖安全审计；
- Dependabot 告警检查；
- patch/minor 依赖升级；
- 完整测试、类型检查和构建；
- 安装包冒烟测试；
- 警告数量和 bundle 趋势记录。

建议每季度执行：

- Node、Electron、Vite、React、FastAPI、SQLModel 兼容性评估；
- Python 运行时版本评估；
- PyInstaller 打包验证；
- Windows 10/11 验证；
- 授权密钥备份与恢复演练；
- 数据库升级与回滚演练；
- 弃用警告基线复查。

高风险依赖应分批升级，尤其是 Electron、Vite/electron-vite、FastAPI/Starlette/httpx、SQLModel/SQLAlchemy、LangChain 生态、LanceDB、transformers/torch 和 PyInstaller。

## 4. 推荐实施批次

1. **质量基线**：重新执行并记录测试、构建、审计、警告和体积数据；不改变产品行为。
2. **Python 时间与测试基础设施**：统一 UTC 语义，迁移测试客户端，消除项目自身弃用警告。
3. **LangChain 官方兼容迁移**：只处理具体弃用点，不移除 LangChain、不重写成熟组件。
4. **Node 安装链路**：迁移 Electron 镜像配置，验证干净环境下的安装。
5. **前端性能观察与可选优化**：记录趋势；有实际收益时再做页面懒加载。
6. **Caret 品牌和文档治理**：统一用户可见品牌，补全授权架构，增加边界检查。

每个批次应独立提交，并满足：

- 相关测试通过；
- 类型检查和构建通过；
- 不新增无法解释的警告；
- 不提交本地数据、缓存和构建产物；
- 不修改或依赖 `legacy/`；
- 涉及安装、授权或数据格式时完成对应冒烟或迁移验证。

## 5. 明确非目标

本维护计划不包含：

- 移除 LangChain 或 `langchain-community`；
- 自行重写 LangChain 文本切块或 BM25 检索；
- 用 SaT 替代知识库 RAG 切块；
- 设置 renderer bundle 的硬性体积预算；
- 为品牌统一而立即更改仓库名、`appId`、数据目录或协议兼容标识；
- 修改 `legacy/` 历史代码；
- 在同一批次中进行大规模依赖升级和业务功能改造。

## 6. 给接手 Agent 的执行提示

开始实施前，应先检查当前工作树并确认其他 Agent 的未提交修改范围，避免覆盖并行工作。随后重新运行实际命令获取最新基线，不应把本文中的历史数量直接当作当前验证结果。

若维护过程中发现某项工作需要改变上述技术边界，例如移除依赖、迁移数据目录或修改授权协议，应先单独形成设计说明和迁移方案，等待确认后再实施。
